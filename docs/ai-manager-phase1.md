# AI 店长第一阶段

## 功能与边界

经营分析负责展示指标和图表，AI 店长复用同一指标口径，形成“问题 → 证据 → 建议 → 风险提示”。本阶段包含：

- 经营简报：所选周期销售表现、履约风险、需关注门店和优先事项。
- 菜品顾问：固定近30天热销、滞销、退菜或高毛利机会，提供人工确认建议。
- 营销助手：根据目标和预算生成方案草稿，没有创建活动、发券或修改价格的接口。
- 经营追问：最近 6 条对话只作为消息上下文。具体指标由只读工具按问题获取，每次调用都会重新校验门店权限。历史消息不存入数据库，切换范围清空。
- 简报与菜品顾问通过后台任务顺序生成，离开页面后不会停止；结果按租户/门店、时间类型和实际日期周期持久化，可恢复当前进度并查看历史版本。

经营分析由真实模型基于受控业务数据生成，不附加硬编码规则证据或建议。模型未配置、Key 无效、额度耗尽或调用失败时返回不可用错误；平台管理员获得网站配置中 AI 模型配置或额度处理提示，普通账号仅显示暂不可用。模型配置可通过后台保存到配置服务数据库，在后续 AI 请求中直接生效，无需重复部署。

## 请求链路

```text
前端工作台（范围与周期）
  → Gateway /ai/**
  → AI 服务：登录、operations:assistant 权限、任务编排
  → Feign：服务端重新生成内部凭据与租户/门店范围
  → 餐饮服务 /inner/restaurant/ai-manager：再次检查范围
  → 现有经营分析服务与汇总表
  → 有界经营指标 + 证据/行动草稿 → 已配置模型（可选）
```

模型没有数据库账号或 SQL 执行能力。经营追问只能调用销售概况、菜品表现和授权门店列表三个只读工具，单次最多 3 次，不能发券、改价或上下架。门店名、菜品名、用户消息和历史对话都不作为权限来源。模型只能接收当前服务端授权范围内的指标；本接口不返回会员姓名、手机号等个人明细。使用外部模型时，仍需确认经营汇总数据允许发送到该供应商。

## 租户与门店隔离

- TENANT 面向当前租户总部，查看全租户总览、门店差异和菜品组合。
- STORE 面向单店，查询前检查门店访问权与当前租户内的门店存在性。
- 门店受限账号不能访问 TENANT，门店选项也由服务端裁剪。
- 平台超管必须先进入具体商户，平台全局模式不允许读取 AI 店长数据。
- Gateway 阻断外部 `/inner/**`，内部接口继续由公共租户拦截器验证调用凭据。

## 数据库压力与刷新机制

本次没有修改用户已优化的 `analysis_refresh_queue`、触发器或分片增量重算任务。AI 页面不启动数据重算，也不新增全租户订单扫描任务。

租户数据继续复用 `TenantAnalysisService` 读取 `analysis_store_daily`、菜品日汇总等既有分析数据；单店复用现有分析查询。数据按任务拆分为 BRIEFING / DISH / FULL，简报和营销不读取菜品组合，菜品顾问不读取销售履约总览。传入模型的榜单限制为最多10条主要样本，历史消息也有长度上限。

注意：榜单样本上限限制的是模型输入，不代表底层 SQL 只扫描10行。大租户的汇总查询仍随门店数、菜品数和日期增长。本阶段没有新增分布式结果缓存、模型调用配额或大租户专项压测，上线应先观察汇总查询耗时及请求频率，再按实际规模配置缓存、并发和配额。

汇总数据的新鲜度取决于现有刷新队列，并非模型生成时间。今日与完整历史周期的比较可能受营业进度影响，建议需人工核验；不能把低样本、新上架或缺失成本直接解释成经营失败。

## 接口

所有 AI 店长入口需 `operations:assistant` 权限，平台超管可通过角色进入，但仍需具体租户上下文。

| 路径 | 用途 |
| --- | --- |
| GET /ai/manager/scope | 可用范围与授权门店 |
| POST /ai/manager/briefing | 经营简报 |
| POST /ai/manager/dish-advice | 近30天菜品顾问 |
| POST /ai/manager/insights | 后台提交经营简报和菜品顾问 |
| GET /ai/manager/records | 查询当前范围和实际周期的任务状态及历史 |
| POST /ai/manager/marketing-draft | 营销草稿 |
| POST /ai/manager/chat | 经营追问 |

POST 请求使用 `scopeType`、可选 `storeId`、`timeRange`（TODAY / YESTERDAY / WEEK / MONTH）；营销额外传 `message`、可选 `budget`；追问额外传 `message` 和可选 `history`。响应包括 `content`、`keyPoints`、`evidence`、`actions`、`scope`、`modelGenerated`、`generatedAt`。经营简报和菜品顾问使用 `keyPoints` 返回可逐项渲染的结构化结论；旧记录的 `content` 仍可作为兼容展示。

## 部署与验收

1. 现有库执行 `sql/vertical-split/45_ai_manager_phase1.sql`，只更新菜单名称，不重建或重绑角色权限。新库种子菜单也已更新。
   然后执行 `48_ai_manager_saas_entitlement.sql`：标准版默认没有 AI 店长，商业版（`pro`）和企业版的新套餐版本包含该权益。标准版租户可由运营分配 `AI 店长加购` 开通；加购价格需先在套餐与权益管理中配置。旧订阅不会自动切换到新版本。
   再执行 `49_ai_manager_call_quota.sql`，商业版与企业版最新版本分别获得每订阅周期 100/500 次，原加购项升级为每周期增加 100 次。四个生成接口每成功生成一次扣 1 次；状态和范围接口不扣次数。后台可调整新草稿版本的额度，发布后分配给租户。
2. 部署餐饮服务和 AI 服务，并发布前端。AI 服务读取公共 Redis/Sa-Token 配置及与其他服务一致的内部调用密钥；已显式排除业务数据源自动配置。
3. 执行 `47_ai_model_runtime_config.sql` 后，超级管理员在网站配置的 AI 模型配置中管理运行凭据。模型、接口地址和 Key 只从数据库动态读取；未保存、关闭模型或缺少 Key 时服务仍可启动并返回不可用提示。
4. 验收总部账号租户视图、门店账号禁止租户视图、跨租户门店拒绝、切换范围不串显示、模型未配置及异常按角色提示，以及营销不产生业务写入。
5. 用真实租户观察汇总数据更新时间和查询耗时；真实模型、Gateway、Nacos、Redis 与数据库联调需要部署环境验证，单元/启动装配测试不能替代这一步。
